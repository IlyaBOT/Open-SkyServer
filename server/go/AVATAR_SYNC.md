# Native Avatar Synchronization

Updated 2026-11-10. This investigation targets Skype 4.2.0.187. End-to-end
avatar synchronization is still unresolved; a database test is not a client test.

## Verified Static Path

REA 6.4.0 with Ghidra 12.1.4 analyzed a static-only PE subset generated by
`patcher/tools/Slice-SkypeAvatar.py`. It copies original pages without changing
their virtual addresses. The carrier must never be executed as a client.

- Canonical unpacked source SHA-256:
  `53ecb3032e76afe1db0a01eeb81e81f81c84e72d7cfae79dad3f197ca171d1ac`.
- Subset SHA-256:
  `0d8cb4d8479531c1909a8c12e2a51eb93511fd56481b9d27b04f1a7a23da2ce8`.
- REA Evidence:
  `ev_af0ac40121d4da759c7825bdef2b326b0c9cb83ee30020314e88aa367e0960eb`.
- Avatar update routine: `005A8DF0`. It reads binary property `0x96`, consults
  `Lib/CentralStorage/SyncAvatar` using a default read from field `0x6A`, and
  conditionally calls the central-storage put/delete paths with `p/avatar`.
  This establishes a conditional upload path, not that a particular XML file
  actually enables it in a running client.

Read-only analysis of the existing full Ghidra project supplements the REA
subset. `InspectSkypeAvatarStorage.java` recovers flow past synchronization
helpers where the earlier decompiler output stopped:

- `0063BF20` calls `EnterCriticalSection` and has a normal `RET 4` path.
- `0063BF70` is the corresponding unlock helper and has a normal `RET` path;
  the imported project had incorrectly marked it non-returning.
- `0074F5E0` constructs central-storage put RPC `0x1789`.
- `0074F960` constructs delete RPC `0x178A`.

The correction changes analysis metadata only, not EXE bytes. Complete private
logs remain in `patcher/diagnostics/avatar-*-20261110*`. Pseudocode parameters
are affected by the client's register calling conventions; assembly and call
sites take precedence over inferred C signatures. Download/listener behavior
still needs a focused trace rather than an assumption based on string names.

## Server Storage Check

`TestNativeAvatarDocumentPersistence` exercises the existing native document
operations using a synthetic, valid JPEG, a temporary SQLite database and test
accounts. It passed on Linux with the native blob worker available:

1. `0x1789` stores `p/avatar` with the client's document checksum.
2. A new `Database` instance returns its checksum in `0x178C`.
3. `0x1788` returns exactly the same document name and JPEG bytes.
4. The reply fits the native encrypted response format for the test image.
5. Another account cannot fetch that private document by its checksum.
6. A wrong checksum is rejected without damaging the stored document.
7. `0x178A` removes the document.

This validates the generic storage path, not an observed upload, rendering in
Skype, a complete encrypted client session, or avatar distribution to contacts.
The current document limit is 12,000 bytes. The avatar-setting client path has
larger image limits, so larger native images and possible record fragmentation
must be characterized before increasing server limits.

## Live VM Checks

The operator changed a built-in avatar in `second@test.lol` on Windows VM
`192.168.1.156`. No `p/avatar` write was observed. A second test closed the
client, set `Lib/CentralStorage/SyncAvatar=1` in both shared and account XML,
restarted and changed the avatar again. At the subsequent inspection the
database still contained only `p/email` and `u/admindev@test.lol` for that user;
there was no avatar document. Enabling this setting alone is therefore not a
verified fix and is not forced into the public portable launcher.

The experimental helper only changes settings using the existing XML parser
and its one-time `.opensky.bak` backup. It refuses to operate if it detects a
Skype process using the selected executable directory. It does not stop the
client, copy a profile, patch an EXE or alter the server database:

```powershell
.\patcher\tools\Set-SkypeAvatarSync.ps1 -Directory C:\SkypePatched -Enabled 1
```

To explicitly disable the setting for a comparison, use `-Enabled 0`.
Run the client through its normal launcher afterward. Retain XML backups
privately: they may contain account settings. Do not redistribute used profiles.
